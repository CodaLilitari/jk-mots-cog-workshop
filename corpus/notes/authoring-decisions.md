# Choose the next COG check

> Public research edition. This is original authored analysis, not a source-code dump. References marked "retained local evidence" were inspected during research but their raw artifacts are not distributed. Binary identities, measured registries and public package identities are included; source execution and retail gameplay remain different evidence grades.


Use this guide to turn a symptom into the smallest useful investigation. It complements the [language reference](language-and-execution.md), verb families (retained local evidence) and eight custom case studies (retained local evidence). The implementation anchors refer to pinned revision `b1be98bd4f170b5384cb71b15443a274aac6a937`; original-binary name tables, executed source probes and game runtime are different evidence levels. The custom examples were inspected and their code sections were parsed/generated, but their VM behavior, original-game behavior and multiplayer outcomes were not executed.

## Start with the loaded object and the intended event

Write down the engine/version/options, episode or mod, archive/loose-file precedence, exact source hash and script role. Identify whether the script is a placed level instance, template class/capture, inventory/weapon/Force bin, static resource or presentation helper. An edit to a file that the game never loads cannot explain an observed change. Resource names, bin assignments and JKL parameter order belong to the same investigation as the COG body.

Describe one required transition in ordinary terms: which event enters, what state permits it, what changes, what a player should observe, when it completes and what cleanup restores. Select a close same-game stock example before generalizing a custom or cheat example. When porting, preserve the required behavior and inspect target contracts; replacing names by resemblance is insufficient.

| An undeclared identifier | Compare local/global lookup, intended initial type/value and resource needs. | A call is absent from the target registry | Read its complete code context, exact spelling and attribution. Check whether it is a typo, extension dependency, shadowed name, unreachable code or intended native call. | The name is absent from that measured native table. It does not prove that the code cannot parse. |
| Final code `end` is absent | Check complete syntax at EOF and keep the separate header transition intact. Use the actual target's load diagnostics when needed. | The two archived missing-end bodies passed the pinned source probe unchanged; appending `end` did not alter their instructions. |

## If the script loads but the wrong handler runs

Build a small event map with five columns: **incoming event**, **declared right-hand event binding**, **local label**, **all label occurrences**, **actual sender path/context**. For `message onStart=startup`, event `startup` should bind local label `onStart`; the two names need not match. A plain helper label reached by `call` needs no message declaration. Conversely, a receiving label alone does not add an engine event handler.

Check both directions: declarations without labels and labels intended as messages without declarations. Then look for duplicates. The pinned loader resolves handler PCs after code generation, and the label pass overwrites a repeated label ID's location. Read the later `damaged`/`activated` blocks in SneakyHaxII instead of assuming the earlier stock-looking block receives the event. A missing `call JESTER;` target is an unresolved label branch, which follows a different VM path from an absent native `JESTER()` function.

Trace entry at the label, explicit `goto`/`call`, all branch exits and fallthrough. Saber’s `BLAH` expression is present in compiled code between one handler's return and the next event label; ordinary event entry skips it. Kyle's `NONSENSE`/`CLOWN` expression is inside a skill branch and potentially reached. These examples establish why both “present in source” and “after a return” need control-flow context.

Relevant implementation: [message header parsing and handler binding](https://github.com/CodaLilitari/OpenJKDF2-MotS-Fixes/blob/b1be98bd4f170b5384cb71b15443a274aac6a937/src/Cog/sithCogParse.c), lines 1089–1112 and 155–160; [label and instruction generation](https://github.com/CodaLilitari/OpenJKDF2-MotS-Fixes/blob/b1be98bd4f170b5384cb71b15443a274aac6a937/src/Cog/sithCogParse.c), lines 781–865; [native-call and label-call execution paths](https://github.com/CodaLilitari/OpenJKDF2-MotS-Fixes/blob/b1be98bd4f170b5384cb71b15443a274aac6a937/src/Cog/sithCogExec.c), lines 120–159 and 246–255. Check class/inventory/link routing and source context in [language and execution](language-and-execution.md) before claiming an event can reach the script in the chosen target.

## If a reached call produces the wrong result

Derive the complete contract from the implementation: arguments in COG order, conversions, invalid-input handling, mode-specific branches, and every pushed result. Reverse the stack-pop sequence to recover call order, but read wrappers and conditional pops before finalizing the signature. Match world indices, inventory bins, sound resource indices, playback handles and network GUIDs to their actual domains.

Three checks prevent common misdiagnoses:

1. **Native spelling and runtime callability.** M.A.C keyblue's plural `ClearWeaponsFlags`/`SetWeaponsFlags` are absent from both original tables; the singular names exist. Its code still parses. In the pinned VM, a non-function target fails the call operation without removing already-pushed arguments. Treat it as a call-contract problem with possible later stack effects, not a successful call or a guaranteed clean no-op.
2. **Return-stack behavior.** `ClearActorFlags`, `SetPulse` and other void operations do not supply a numeric result. SneakyHaxII force-well nests `ClearActorFlags` in inventory arguments and arithmetic; those expressions can consume earlier operands. An underflow fallback in `PopFlex` is not the verb's return value. Use explicit side-effect statements and a separate numeric expression in an authored repair. `ReturnEx(value)` also sets a return-value field without ending the handler; add `return;` where control flow should stop.
3. **Evaluation and conversion.** The pinned logical operations evaluate both operands; use nested guards for calls requiring valid objects. The VM's integer-pop conditional/inequality paths can truncate fractions, so use explicit comparisons appropriate to the value. Read the documented source caveats before relying on familiar C semantics.

## If objects, motion or timing diverge

| Situation | Decision to make | Concrete evidence to inspect |
| --- | --- | --- |
| Creation can fail | What is the invalid sentinel, and when does the script enter its active state? | Grapple unconditionally starts polling after a projectile result; `if(handle)` is not an index-validity test. Initialize the intended sentinel, check creation and clear stored handles during cleanup. |
| A saved thing survives a delay | Does it still identify the same live object? | Destruction and index reuse can invalidate meaning; revalidate after sleep/timers and keep ownership explicit. |
| Motion loses momentum | Is the operation replacing velocity or adding force/velocity? | Jet-pack branches use different arguments: earlier branches add to current velocity, the final branch builds from a look vector. `SetThingVel` and `ApplyForce` are distinct contracts. |
| A JK rotation behaves differently in MotS | Does the target interpret orientation as Euler angles or a look direction? | Pinned JK `CreateThingAtPos` builds an Euler rotation; MotS normalizes a nonzero look vector and treats insertion offset differently. MotS's `CreateThingAtPosOld` is an explicitly reviewed compatibility option, not a universal replacement. |
| Stopping a timer/pulse still changes state once | Should cleanup end the current invocation? | Jet-pack disables future pulses but falls through to sound and motion. Place the required control-flow exit explicitly. |
| A tiny interval does not produce expected timing | How often does the game process the COG, and what happens after a long frame? | The source sends at most one due pulse per processing call and schedules from current time. A requested 0.001-second interval is not a measured 1 kHz delivery rate. |
| Rotation drifts near second boundaries | Is elapsed time monotonic, or a wrapped fractional value? | Edward's `%1` clock leaves the old `timing` in use on wrap/equal samples. Inspect elapsed-time and wrap handling separately from angle math. |
| Repeat activation leaves old effects | Who owns each pending timer, sound channel and created thing? | Keyblue stores one projectile while scheduling IDs from it; later activation can replace that state before an earlier timer arrives. Jet-pack repeatedly creates sounds while retaining one handle. |

These rows identify what to test, not observed crashes or gameplay outcomes. ## If multiplayer visibility or checksum behavior differs

Separate **where a handler executes**, **which call transmits state**, **which peer owns the gameplay change** and **whether joining content is accepted**. A `local` symbol declaration, a script's `0x40` local bit, the `0x200` no-sync bit, explicit trigger transport and a checksum comparison are different mechanisms. Follow the dispatcher and the concrete verb; a local visual script can invoke network-visible operations, and a source build with checksum rejection disabled cannot certify original-game acceptance.

For checksum questions, preserve the exact executable, mount/load order, original and edited content, and distinct peer inputs. The original binaries inspected in this corpus feed a word count to a byte-consuming checksum helper; that does not make every tail edit safe. Adding compiled but unreachable code can still change instruction count, positions and prefix coverage. The parser adapter's generated words have different symbol numbering and are not a retail checksum calculator. Use [checksums and retail](checksums-and-retail.md) for the actual evidence and a bounded experiment design.

## Choose verification that can answer the question

Record each result at its actual level: lexical availability, accepted code-section grammar, source-derived behavior, static original-binary evidence, a loaded script in the intended engine, observed lifecycle behavior, or connected-client observations. A passing earlier level does not imply the later ones. Keep initial source and repaired candidate hashes separate.

For a small repair, select the normal event and the closest meaningful counterexample: failed creation; repeated activation; zero/exhausted resource; wrap/long frame; death/respawn; invalidated object; late timer; or a remote initiator. Capture the state needed to distinguish hypotheses, not just whether a visual appeared. For a port, test the exact semantic difference being changed. For multiplayer, identify both clients and their content, then observe authority, remote results and cleanup. Report unexecuted cases plainly; the research corpus provides the evidence and test design, not a substitute for these observations.
